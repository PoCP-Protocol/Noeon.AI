# NOEON 通用 AI 编程语言路线图（2026-2027）

状态: Draft for Execution
版本: 1.0
更新时间: 2026-06-09
适用范围: 从“可运行的 AI 语言系统”走向“可规模化落地的通用 AI 编程语言”

---

## 1. 北极星目标

在 12 个月内，把 Noeon 从“强能力原型”推进到“可被团队长期采用的通用 AI 编程语言”，满足以下四个标准:

1. 语义可证明: 核心语义有可机检规范，跨执行路径结果一致。
2. 工程可规模: 在多团队、多仓库、多模型场景可稳定开发和发布。
3. 生态可复用: 有包生态、互操作层、标准治理与审计能力。
4. 迁移可落地: 传统栈 (TS/Python/Java/.NET) 能低摩擦接入。

---

## 2. 当前基线（2026-06）

已完成能力:

1. Canonical IR-first 已成为默认执行路径。
2. Legacy 路径已进入 sunset 计划（ADR-004）。
3. Next runtime 已 kernel 化，关键治理/演化/记忆链路可回归验证。
4. Surface 判定与 parse-dispatch 关键回归已补齐。

当前短板:

1. 缺少完整形式化语义与兼容性承诺文档。
2. 缺少效果系统（副作用、外部调用、成本/时延）与静态检查闭环。
3. 缺少包生态与跨语言互操作规范。
4. 缺少生产级运行时 SLO、容量与故障演练体系。

---

## 3. 12 个月执行路线

## Phase 1（Q3 2026）语义与兼容性封板

目标: 把“语言行为”从实现细节提升为正式契约。

交付:

1. 发布 Noeon 语义契约 v1.1（操作语义 + 未定义行为边界）。
2. 发布兼容性策略（SemVer + 废弃周期 + 迁移规则）。
3. 建立语义黄金集（跨 surface、跨 profile、跨 executor）。
4. 增加 strict/unknown/governance 优先级的契约测试矩阵。

验收指标:

1. 语义契约测试覆盖率 >= 95%（核心节点）。
2. 同输入跨执行路径一致性 >= 99.9%。
3. 每次发布都产出兼容性变更报告（自动生成）。

---

## Phase 2（Q4 2026）类型与效果系统

目标: 把不确定性与副作用纳入类型系统，减少运行时事故。

交付:

1. 引入 Effect 标注（network/model/io/memory/human-gate）。
2. 引入成本与时延预算类型（budget/latency/token）。
3. 新增静态 lint 规则与阻断级别（warn/error/policy-fail）。
4. IDE/LSP 增强: 效果流可视化、风险提示、预算超限提示。

验收指标:

1. 线上回滚率下降 >= 40%。
2. 预算越界问题在静态阶段发现率 >= 80%。
3. 高风险 effect 调用零“无标注提交”。

---

## Phase 3（Q1 2027）运行时与可观测性生产化

目标: 让 Noeon 运行时支撑生产负载与排障。

交付:

1. 运行时 SLO 套件（成功率、P95/P99、恢复时间、成本波动）。
2. 分布式执行能力（任务取消、重试语义、幂等保证、背压）。
3. 全链路追踪（源码 -> phase -> effect -> 模型调用 -> 审计记录）。
4. 故障注入与演练剧本（网络抖动、模型降级、策略阻断）。

验收指标:

1. P95 稳定性达到目标线（由业务定义，默认 <= 2x 基线）。
2. MTTR 缩短 >= 50%。
3. 审计追踪可还原率 100%。

---

## Phase 4（Q2 2027）生态与互操作

目标: 从“语言系统”走向“开发平台”。

交付:

1. 包管理与注册中心最小可用版（发布、依赖、签名、回滚）。
2. 官方互操作 SDK（TS/Python 首发，Java/.NET 跟进）。
3. 标准连接器层（OpenAPI、MCP、SQL、Queue、Vector）。
4. 迁移工具链（代码扫描、自动映射建议、风险评估报告）。

验收指标:

1. 生态包数量 >= 100（核心可用包 >= 30）。
2. 外部项目接入周期缩短到 <= 2 周。
3. 跨语言项目中 Noeon 模块复用率 >= 60%。

---

## 4. 横向保障（全阶段持续）

1. 安全与治理
- 策略版本化、执行证据、可追责审计。
- 人审门控（human gate）必须可配置且可回放。

2. 文档与教育
- 建立三层教程: 脚本层、工程层、架构层。
- 建立反模式与事故案例库。

3. 发布工程
- 每次发布必须包含: 变更摘要、兼容性评估、回归报告、迁移提示。

---

## 5. 组织与角色建议（最小配置）

1. 语言内核组（2-3 人）
- 负责语义、编译、执行器、类型/效果系统。

2. 运行时与平台组（2-3 人）
- 负责 SLO、分布式执行、观测、稳定性。

3. 工具链与生态组（2-3 人）
- 负责 LSP、CLI、包管理、SDK、连接器。

4. 质量与治理组（1-2 人）
- 负责 conformance、策略审计、发布门禁。

## 6. 30 天启动清单（可立即执行）

Week 1

1. 冻结 v1.1 语义范围（明确哪些语义进入“稳定承诺”）。
2. 建立统一路线看板（Epic -> Milestone -> Gate）。
3. 建立发布门禁模板（回归、兼容、审计三张报表）。

Week 2

1. 开始语义黄金集建设（先覆盖治理优先级 + strict/unknown）。
2. 定义 effect 分类与标注语法草案。
3. 补齐 README 与 Canonical 文档链接一致性。

Week 3

1. 增加 lint 原型规则（至少 5 条高价值规则）。
2. 增加 trace 到源码位置映射（第一版）。
3. 完成第一轮故障演练脚本（模型超时/降级）。

Week 4

1. 发布 v1.1-alpha 预览（内测）。
2. 输出迁移指南草案（legacy -> canonical）。
3. 复盘指标并锁定下一季度资源投入。

## 7. 风险与对策

1. 风险: 新能力扩张过快，语义不稳定。
- 对策: 新特性默认 experimental，必须通过语义黄金集后再稳定化。

2. 风险: 文档与实现继续漂移。
- 对策: 每次发布自动校验文档引用与命令可执行性。

3. 风险: 生态推进慢于内核演进。
- 对策: SDK/连接器与内核并行排期，设置独立里程碑。

4. 风险: 团队容量不足。
- 对策: 先保语义封板和运行时稳定，生态分阶段渐进。

---

## 8. Definition of Success（2027-06）

满足以下条件即视为“通用 AI 编程语言阶段性达标”:

1. 语义层: 关键语义稳定承诺 + 自动兼容性报告。
2. 工程层: 生产 SLO 稳定 + 可回放审计链路。
3. 生态层: 可用包生态 + 主流语言互操作 + 迁移工具可用。
4. 组织层: 发布流程标准化，季度目标可复盘。

## 9. 建议的首个执行里程碑（M1）

里程碑名称: 语义封板与治理可证明（6 周）

交付清单:

1. 语义契约 v1.1 草案
2. 治理优先级 conformance 套件
3. strict/unknown 契约矩阵
4. 发布门禁自动报表（兼容 + 回归 + 审计）
5. 默认发布入口使用 `npm run gate:all`，门禁结果以 `artifacts/release-gate/release-gate.latest.json` 和 `artifacts/release-gate/release-gate.latest.md` 为准

M1 通过标准:

1. 主干每次提交自动给出兼容风险等级。
2. 治理相关回归为零漏检。
3. 发布候选包具备一键回滚与证据链。
4. 发布门禁的 PASS/WARN/FAIL 判定可被机器读取并在文档中一致解释。
